# 약관 문서 및 동의 기록 준비

## 현재 구현 범위

- `/terms`, `/privacy`는 로그인 없이 접근 가능한 준비 페이지다. 개인정보 수집·이용 필수 동의 안내와 처리방침의 역할을 구분했고 이메일/SMS 마케팅 안내는 각각의 앵커로 연결한다.
- 실제 문서가 없어 모두 draft, version/effectiveDate는 null이다. 사업자 정보·보유 기간·수탁업체 등을 추측하지 않았다.
- `lib/legal/documents.ts`가 문서 내용·경로·상태·버전·시행일의 중앙 원본이다. 공개 버전 형식은 `YYYY-MM-DD.rN`, 시행일은 `YYYY-MM-DD`. 같은 날짜의 개정은 rN을 증가시키며 공개한 버전의 본문을 덮어쓰지 않고 보존해야 한다.
- `lib/supabase/consents.ts`는 필수 terms/privacy, 선택 marketing_email/marketing_sms, 각 boolean 선택값, 검증을 관리한다. 전체 동의는 개별 선택값에서 계산한다.
- 회원가입은 필수 두 항목을 별도로 확인하고 선택 항목 false도 허용한다. draft 선택은 입력 확인에만 쓰며 localStorage, Auth metadata, 쿠키, DB에 저장하지 않는다.
- 현재 Footer가 없어 별도 Footer를 추가하지 않았다. 가입 화면의 보기 링크는 새 탭으로 열어 입력 상태를 유지한다.
- `getActiveConsentVersions()`는 draft가 하나라도 있으면 null이다. active 변경만으로 DB 저장이 활성화되는 구조가 아니다. INSERT 경로, 신규 migration, 원격 DB 변경은 없다.

## 인증 전 선택을 연결하는 설계 — 아직 구현/활성화하지 않음

확정 문서가 준비되면 다음 흐름을 구현한다. 현재 callback의 PKCE 교환·세션 쿠키 반환은 유지한다.

1. 회원가입 요청 전 동일 출처 Server Action에서 필수 선택, boolean 타입, 서버의 활성 문서 버전과 시행일을 검증한다. 사용자 입력 버전이나 user_id는 받지 않는다.
2. 서버가 임의의 intent ID, 네 개 선택값(true/false), 서버가 제공한 문서 버전 및 본문 식별값, 정규화한 가입 이메일의 HMAC, 발급/만료 시각을 서명한 짧은 수명의 HttpOnly·SameSite=Lax 쿠키를 발급한다. 운영 환경에서는 Secure를 사용한다. 비밀번호나 이메일 원문은 포함하지 않으며 서명키는 서버 전용이다. 별도 이메일 존재 확인은 하지 않는다.
3. 이메일 인증 후 getUser()로 검증된 사용자와 인증된 이메일을 얻는다. 서명·만료·이메일 HMAC·문서의 기록 가능 여부가 일치해야만 그 auth UUID와 연결한다. signUp 응답의 user.id는 기존 계정에 대해 가려진 값일 수 있으므로 바인딩 기준으로 쓰지 않는다.
4. 동시 callback/재시도를 고려해 intent ID를 유일 키로 소비하고 네 개 동의를 한 트랜잭션으로 INSERT한다. user_id는 검증된 사용자, recorded_at은 DB 기본값만 사용한다. 마케팅 false도 기록한다. 기존 이력 UPDATE/DELETE는 하지 않는다.
5. 성공 응답에서 intent 쿠키를 삭제한다. 응답 유실이나 새로고침으로 재시도돼도 이미 소비한 intent에는 행을 추가하지 않는다. 미래 동의 변경에는 새로운 intent ID를 사용하므로 철회/재동의를 막지 않는다.
6. 다른 브라우저·쿠키 소실·만료·이메일 불일치·문서 개정 시 자동 확정하지 않는다. 인증 후 실제 문서를 다시 보여주고 명시적인 재동의를 받는다. consent 저장 실패는 Auth 세션 교환 성공과 분리해 재시도 가능한 상태로 안내한다.

## 활성화 전에 필요한 DB 보강

현재 RLS는 본인 UUID INSERT만 허용하고 UPDATE/DELETE를 막는다. recorded_at/id INSERT 컬럼 권한도 없으므로 시각·ID는 DB가 결정한다. 다만 document_version은 비어 있지 않은 문자열만 검사하며, authenticated 역할에 직접 INSERT가 허용되어 있다. 따라서 현재 정책만으로는 임의 버전, 서명 위조, 중복 이력을 막을 수 없다.

실제 기록 기능을 만들 때는 새 migration에서 승인된 문서 버전 목록과 intent 소비의 유일성/원자성을 추가하고 직접 INSERT 경로를 통제해야 한다. RPC를 공개한다면 auth.uid() 일치뿐 아니라 서버 발급 서명의 진위를 DB의 신뢰 가능한 경계에서도 검증해야 한다. 클라이언트가 같은 RPC에 임의 payload를 보내 우회할 수 있으면 안 된다. 서명 검증키의 비공개 보관과 RPC 권한까지 함께 검증한 뒤 활성화한다. 단순 SELECT 후 INSERT 또는 모든 user/type/version 조합의 영구 UNIQUE는 적절하지 않다(경쟁 조건 또는 미래 재동의 제한).

draft 문서에 대한 기록을 만들지 않기 위해 이번 단계에는 이 migration/RPC/쿠키 전달을 억지로 추가하지 않았다. 현재 선택값은 인증 후 이력으로 이어지지 않는다.

## 운영자가 확정해야 할 정보

- 최종 이용약관 본문, 개인정보처리방침, 필수 수집·이용 동의문, 이메일/SMS 마케팅 동의문 및 검토 승인.
- 실제 운영 사업자명·대표자·사업자등록번호·주소·고객 문의처와 해당하는 통신판매업 정보.
- 실제 수집 항목·목적·처리 근거·보유/파기 기준·동의 거부 안내.
- 실제 위탁/제3자 제공/국외 이전 관계, 개인정보 보호 담당자/문의처, 권리 행사와 수신 철회 방법.
- 각 문서 시행일과 버전, 이전 본문 보존 방법, 문서 개정 시 재동의 정책.
- 가입 선택을 보관할 intent 만료 기간과 재시도 정책, 서버 서명키 관리.

## 검증 범위 및 수동 확인

필수 하나라도 해제하면 가입 차단, 필수 둘만 체크하면 마케팅 미동의로 가입 가능, 전체 동의 후 개별 해제 시 전체 동의 해제를 확인한다. 링크가 새 탭에서 열리고 draft/버전 미확정 안내가 나오는지 확인한다.

기존 이메일 응답 UX, 이메일 인증/세션 유지, 로그인/로그아웃, 마이페이지 보호, 프로필 저장/전화번호 표시의 실계정 흐름은 운영자가 브라우저에서 확인해야 한다. 실제 회원정보나 원격 동의 이력은 이번 작업에서 변경하지 않는다. E~H(실제 consent 사용자 연결·동시 재시도)는 기록 기능 활성화 후 검증 대상이며 완료로 간주하지 않는다.
