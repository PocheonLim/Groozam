# 마이페이지 배송지 관리

화면: `/mypage?section=addresses`. 공식 다음/Kakao 우편번호 검색으로 우편번호와 기본 주소를 입력하고 상세주소는 직접 입력합니다. 기존 `PhoneInput`의 010 휴대전화 형식과 자동 하이픈 표시를 재사용합니다.

## 배포 전 DB 작업

`migrations/20260929000000_address_write_rpc.sql`을 기존 migration 다음에 적용해야 저장·삭제·기본 배송지 설정이 동작합니다. 2026-09-29 사용자 요청으로 앱 환경변수와 연결된 프로젝트가 일치함을 확인하고, dry-run에서 이 migration 하나만 미적용임을 확인한 뒤 원격 Supabase에 적용했습니다. 적용 후 API 응답이 함수 미존재(PGRST202)에서 비로그인 실행 권한 거부(42501)로 변경된 것을 확인했습니다. 다른 환경에 배포할 때도 migration을 적용하세요.

이 migration은 `groozam_write_address` 함수와 실행 권한만 추가합니다. 기존 테이블, 데이터, RLS, 테이블 권한은 변경하지 않습니다. 이미 존재하는 `addresses_one_default_per_user_idx`가 사용자별 기본 배송지를 최대 1개로 제한합니다.

RPC는 `SECURITY INVOKER`로 기존 RLS를 따르고 `auth.uid()`로 소유자를 결정합니다. 사용자별 transaction advisory lock으로 앱의 변경 요청을 직렬화하고, 기존 기본 배송지 해제와 새 기본 배송지 설정을 같은 트랜잭션에서 처리합니다. 실패하면 이전 기본 배송지 해제도 롤백됩니다. 함수를 직접 호출해도 인증·소유권·입력 검증이 적용됩니다. anon은 실행할 수 없습니다.

기존 테이블 직접 쓰기 권한은 유지합니다. 직접 REST/SQL로 변경하는 요청은 RPC 잠금을 사용하지 않지만, 기존 unique index가 중복 기본 배송지를 차단합니다. 충돌하면 요청이 실패하며 앱은 다시 확인하도록 안내합니다.

## 동작과 입력 정책

2026-09-29 후속 migration `20260929010000_reassign_default_address_on_delete.sql`을 원격 DB에 적용했습니다. 기존 RPC의 삭제 분기만 변경하여 삭제와 기본 배송지 재지정을 동일한 사용자별 잠금/트랜잭션 안에서 수행합니다. 테이블·RLS 변경 및 기존 데이터 일괄 수정은 없습니다.

- 최초 배송지는 기본 배송지로 등록합니다.
- 기본 배송지를 삭제하면 남은 배송지 중 가장 최근 등록한 주소(created_at 내림차순, 동률 시 id 순)를 기본 지정합니다. 마지막 배송지 삭제 시에는 빈 목록이 됩니다. 일반 배송지 삭제는 기존 기본 배송지를 유지합니다. 수정에서 기본 설정을 직접 해제하는 기존 동작은 유지합니다.
- 배송지명/받는 사람: 필수, 각 50자 이하.
- 휴대전화: 필수, 기존 프로필 정책과 동일한 010 숫자 11자리. DB에는 숫자만 저장합니다.
- 우편번호: 숫자 5자리. 기본 주소: 필수, 300자 이하.
- 상세 주소: 선택, 300자 이하. 기존 NOT NULL 컬럼에는 빈 문자열을 저장합니다.
- 배송 요청사항: 선택, 500자 이하. 비어 있으면 null입니다.
- 클라이언트와 Server Action에서 검증하고, RPC에서도 형식과 길이를 검증합니다.
- 조회와 Server Action은 서버 `getCurrentUser()`의 `getUser()` 확인을 거칩니다. 전달된 user_id는 사용하지 않습니다.

## 검증 결과

- TypeScript, ESLint, production build 통과.
- 임시 로컬 PostgreSQL(PGlite)에 migration 원문을 적용하여 CRUD, 첫 배송지 기본 설정, 기본 변경, 실패 시 트랜잭션 롤백을 확인했습니다. 후속 삭제 정책 변경에서는 기본 배송지 자동 재지정, 일반 배송지 삭제 시 유지, 마지막 배송지 삭제, 타인 배송지 접근 차단을 확인했습니다.
- 두 가상 회원으로 자신의 목록만 조회되는지, 타인 ID의 RPC 수정/삭제/기본 변경과 직접 UPDATE/DELETE가 차단되는지 확인. 타인 소유 INSERT, 소유자 컬럼 변경, anon RPC 실행 차단 확인.
- 기존 unique index의 중복 기본 배송지 거부와 필수값/전화번호/길이/우편번호 검증 확인.
- 임시 Node 검증으로 Server Action 비로그인 거부, 잘못된 ID/입력 거부, 임의 user_id 무시, 삭제 확인 취소, 동시 클릭 시 클라이언트 요청 1회 확인.
- 기존 테스트 러너/테스트 파일은 없으며 앱 의존성은 추가하지 않았습니다. 임시 검사 스크립트는 Git 제외 경로에서 실행했습니다.
- 원격 회원/배송지는 생성하지 않았습니다. 실제 로그인 브라우저 CRUD, 모바일 실기기, 독립 DB 연결의 동시 요청 부하 테스트는 미실행입니다.

## 직접 확인할 순서

1. 새 migration 적용 후 로그인하여 배송지 관리에 진입합니다. 비로그인 시 로그인 페이지로 이동하는지 확인합니다.
2. 비어 있는 목록에서 배송지를 추가합니다. 이름·수령인·010 휴대전화를 입력하고 우편번호 찾기로 주소를 선택합니다. 자동 입력과 상세주소 포커스 이동, 휴대전화 자동 하이픈과 잘못된 입력 안내를 확인합니다.
3. 두 번째 배송지를 추가하고 수정합니다. 기본 배송지를 변경한 뒤 새로고침해 표시가 하나인지 확인합니다.
4. 삭제를 취소한 뒤 유지되는지 확인하고, 다시 승인하여 삭제합니다. 기본 배송지 삭제 후 남은 배송지 중 가장 최근 등록한 주소가 기본으로 지정되어야 합니다. 수정 중인 배송지 카드는 목록에서 숨겨지고 취소하면 다시 표시되어야 합니다.
5. 두 탭에서 서로 다른 배송지를 빠르게 기본으로 지정하고 새로고침합니다. 기본 표시는 최대 하나여야 합니다.
6. 다른 계정으로 로그인하면 첫 계정 배송지가 보이지 않아야 합니다. 네트워크 장애 시 오류 안내와 버튼 재활성화를 확인합니다.
7. 모바일과 PC에서 목록, 추가/수정 폼, 긴 주소 표시를 확인합니다.

## 주소 검색 연동

`app/components/AddressSearch.tsx`가 추가/수정 폼의 주소 필드 3개를 담당합니다. 공식 가이드(https://postcode.map.kakao.com/guide)의 키 없는 우편번호 서비스를 사용하며 `next/script`의 afterInteractive 및 중복 로딩 방지를 사용합니다. 공식 스크립트는 `https://t1.kakaocdn.net/mapjsapi/bundle/postcode/prod/postcode.v2.js`입니다. 인증 정보나 Supabase 설정은 전달하지 않습니다.

모바일 고정 레이어 대신 페이지 내부에 `embed()`로 검색 UI를 표시합니다. 선택한 도로명/지번 주소를 사용하며 우편번호·기본주소는 readOnly입니다. 새 주소 선택 시 상세주소를 비우고 포커스를 이동합니다. 동일 주소 재선택과 검색 취소는 상세주소를 유지합니다. 스크립트 오류와 15초 로딩 지연은 한국어로 안내하고, unmount/닫기 이후 검색 콜백은 무시합니다. 스크립트 로딩 자체가 실패하면 페이지를 새로고침해야 합니다.

추가 변경에 대해 TypeScript·lint·production build를 통과했습니다. 임시 Node 검사로 추가/수정 초기값, 선택한 도로명/지번 반영, 상세주소 초기화/유지, 포커스 호출, 취소, 스크립트 실패 분기를 확인했습니다. 기존 임시 CRUD 검사 파일은 현재 작업 시작 시 존재하지 않았고 별도 테스트 러너도 없습니다. 실제 외부 검색 UI와 로그인 브라우저 CRUD는 이번 변경 후 자동 검증하지 않았습니다.

브라우저에서는 다음을 확인하세요.

1. 추가 폼에서 키보드로 우편번호 찾기를 열고 도로명/지번 검색 결과를 각각 선택합니다. 우편번호와 주소가 채워지고 상세주소로 포커스가 이동해야 합니다.
2. 배송지를 저장한 뒤 수정 폼을 열어 기존 주소가 유지되는지 확인합니다. 다른 주소 선택 시 상세주소가 비워지고, 검색 닫기로 취소하면 기존 값이 유지되어야 합니다.
3. 개발자 도구의 Network에서 공식 스크립트 URL을 차단하고 새로고침하여 검색을 엽니다. 오류 안내가 표시되고 다른 입력값은 유지되어야 합니다. 차단을 해제하고 새로고침하면 다시 검색할 수 있어야 합니다.
4. 모바일 너비(320/390px)와 실제 휴대전화에서 검색 결과가 가로로 넘치지 않는지, 닫기·주소 선택·상세주소 입력이 가능한지 확인합니다.
5. 저장·기본 배송지 변경·삭제를 다시 확인합니다. Server Action/DB/RLS/PhoneInput은 이번 주소 검색 작업에서 변경하지 않았습니다.

주문 배송지 복사, 배송비 계산, 배송 가능 지역 검증은 이번 범위에 포함하지 않았습니다.
